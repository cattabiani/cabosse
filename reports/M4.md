## The lane

`rtl/dot_lane.sv` computes FP32 dot products of BF16 rows in the order of
numerics.md, section 3, the order the golden model's `dot` follows.

<!-- begin: shape -->
<!-- end: shape -->

- **Input:** one beat per cycle with valid/ready: a group of pairs (w, x),
  a mask of the elements that are there, and `last` at the row's end. A
  missing element leaves its partial sum unchanged, anywhere in a row.
- **Units:** each multiply-add unit owns its share of the partial sums,
  kept in a small accumulator file read and written by the group's index.
  A cycle without input costs that cycle only: the bubble tests count it.
- **Final sum:** at a row's end its partial sums go to a level-1 buffer;
  one more adder adds them in the fixed tree like a conveyor belt, one
  queue per tree level, while the lane runs the next rows. Rows shorter
  than the tree's adds make `ready` drop at their end, with the same bits.
- **Output:** one FP32 result per row, in row order, valid/ready.

Changed from the answers at the milestone's start (PLAN.md, M4): the
final sum was first built with three contexts and a scheduler choosing
among every pending add; the first Vivado run showed it took nearly half
the lane, and the owner chose the conveyor belt, which has the same bits.
Full rate is tested from the exact bound, the tree's adds times the pairs
per cycle, rather than from the 64 elements first agreed.

## Tests

- `verif/tests/test_dot_lane.py` (cocotb, every product pipeline depth):
  every row length up to 20 and random ones, single bubbles at each beat,
  runs of bubbles, random gaps, random output ready, the output held for
  long stretches, masks anywhere, -0 rows, special values. Full rate: no
  stall on long rows, even with gaps.
- `verif/tests/test_dot_lane_bulk.py` (Verilator bulk driver
  `verif/bulk/dot_lane.cpp`): model-like rows at SmolLM2's lengths and
  long p.V rows, random bits, products near both ends of FP32's range,
  cancelling rows, missing elements; a test counts each family's result
  classes. Cycle count of full-rate rows. The flush-to-zero build. Slow:
  the volume run and one SmolLM2 decode step's real rows.
- `verif/tests/test_rtl_checks.py`: lint and Yosys synthesis of the lane
  and its harness, an elaboration check on `E`, and a Yosys logic-depth
  proxy for timing.
- Mutation checks (hand-made RTL bugs, PLAN.md): every one caught except
  two that give the same results (the root's oldest-context condition of
  the first design; taking the shallowest tree level first).
- Reviews: `/code-review` and `/simplify` on the bulk tests; their fixes
  are in PLAN.md.

## Open issues

1. **Area.** The engine's lanes take the share of the part in the table
   above before anything else is placed. Whether everything fits, and
   still meets 250 MHz, is known only at the first full build (M8, M9).
   The four multiply-add units are now most of a lane, so a further
   saving would have to come from them.
2. **Subnormals on F2 (D-016).** The flush-to-zero lane is tested, but
   its F2 resource cost was not measured: it comes with the first build,
   as planned in M3.
3. **Timing proxy.** The Yosys logic-depth limit is the lane's own value
   when written; it catches growth, not a timing failure. Vivado has the
   last word.
4. **Real data at long positions.** The real-data test runs at an early
   position, so its p.V rows are short; long p.V rows are tested with
   synthetic values only.
5. **For M5.** A valid/ready loop shared by the bulk drivers (one copy
   now, in the lane's driver); a trace hook in the golden decoder that
   names each dot-product call site, instead of the real-data test's
   call counting; driving many lanes' datapaths from one control (the
   lane's control is one block for this).
