# M9 checkpoint: SmolLM2-135M-Instruct on F2, measured

The core (`rtl/core.sv`: controller, 128-lane engine, vector unit, 32 HBM
ports) was built once in AWS's F2 shell and run on an f2.6xlarge. The build
missed 250 MHz, so it runs at 100 MHz (D-072; 250 MHz is M10's). The tables
are generated by `scripts/report_m9.py` from the runs' logs in
[data/f2/](data/f2/), [data/M9.json](data/M9.json) and the perf model; a
test fails if they are stale.

## Against the perf model and the bandwidth bound

Run 3's long fixture, per position. The perf model is `model/perf.py` in
order (memory and engine overlapped, the vector unit and the commands after
them), with the core and its ports at 100 MHz. The bandwidth bound is the
bytes a token reads and writes (weights, KV cache, logits) over the 32
ports' raw rate at 100 MHz, one 32-byte beat a cycle each (102.4 GB/s; M8
measured each port at that rate).

| 0–127 | 194.8 | 203.0 | -4.0% | 373.8 | 52% | 54% |
| 46–173 | 192.7 | 200.8 | -4.0% | 369.5 | 52% | 54% |
| 917–1044 | 159.0 | 164.7 | -3.4% | 303.6 | 52% | 54% |
| 45–1044 | 174.2 | 181.0 | -3.8% | 333.4 | 52% | 54% |

<!-- begin: spread -->
At each of the long run's 1045 positions the measured cycles are +3.4% to +4.3% off the model (median +3.9%).
<!-- end: spread -->

The model's terms of one step, in cycles:

<!-- begin: terms -->
| position | measured | model, in order | memory | engine | vector | commands |
|---|---|---|---|---|---|---|
| 0 | 508,285 | 488,876 | 284,647 | 297,382 | 186,162 | 5,332 |
| 1023 | 630,990 | 610,076 | 359,073 | 363,772 | 240,972 | 5,332 |
<!-- end: terms -->

The model counts slightly fewer cycles than the core at every position, by
about the same share, so it predicts the core well. The memory and the
engine are close to even at 128 lanes, and the vector unit's time comes
after them, about a third of a step: in order, the model itself reaches
only about half the bound. Overlapping or shortening the vector unit's work
(Q-30, Q-32) is what moves the core toward the bound; a faster clock (M10)
speeds everything up and leaves the share about where it is.

## Against the F2 host's CPU (D-056)

Same session as run 3, same model, the f2.6xlarge's 12 cores. The core's
figures are from its cycles over the window; the long run ends at 1044,
so its last window starts at 917, not 1023.

**How to read this:** the columns are two separate ways of running the
same model, not one on top of the other.

- llama.cpp runs SmolLM2 on the host's CPU alone, without the FPGA.
- The core runs it on the FPGA; the CPU only hands it a token and reads
  back the result each step.

A negative share means the core is that much slower than the CPU running
the model by itself. Using the core does not slow the CPU down.

This first build does not yet beat a 12-core server CPU on a model this
small. The reasons, measured above:

- **Clock:** it runs at 100 MHz, not the 250 MHz it was designed for (M10).
- **Vector unit:** its work comes after the memory reads instead of beside
  them, which keeps the core at about half of what the memory bandwidth
  allows.
- **Logits' read:** in wall-clock time, reading the logits back over PCIe
  takes longer than the core's own work (Q-34).

## Open

- Timing at 250 MHz: M10 (D-072), with its ≥ 50% of the bandwidth bound.
- The logits' read dominates the wall clock (Q-34).
- PCIS copies: the second of five writes is about four times slower than
  the others, and the first read slower than the rest, in every run (table
  above); the cause is not known. It does not matter for M9: SmolLM2's
  weights load in well under a second.
- The vector unit's dependent commands and reductions (Q-30, Q-32) are
  the next speed work after timing.
- Gemmini's weight format is not recorded, so its bytes/s is not given;
  stories260K's shape is from llama2.c's model card, to verify.
- The `transformers` baseline started on a busy machine (see above).
