## The core

`rtl/core.sv`: the controller, the engine (M5) and the vector unit (M6),
on F2's 32 HBM ports.

- **Controller** (`rtl/controller.sv`): the AXI-Lite registers, a 64 KiB
  command buffer and a sequencer that hands each command to its unit, a
  command a cycle at most. A small scoreboard sets the engine's waits and
  gos and the stops in hardware (D-068), the same as
  `commands.engine_waits`, `stops` and `kv_waits`. An unknown opcode or a
  missing `END` gives STATUS error and the ERROR register.
- **Buffers:** the engine reads x and writes its results through the vector
  unit's ext port; P has a second read port, a copy of its banks (D-069).
- **Runtime** (`sw/`): the host side, six calls to a platform
  (`reg_write`, `reg_read`, `mem_write`, `mem_read`, `run_until_done`,
  `read_logits`). It lays out the model in device memory (D-040), checks
  the command list before writing it, and runs one decode step per token;
  the host says "go" once a token. At the end of the context window it
  stops with a message.
- **Simulation platform** (`sw/sim_platform.py`): the core under Verilator
  in a child process (`verif/bulk/core.cpp`), driven over stdin and
  stdout. M9's F2 platform implements the same six calls.

## SmolLM2 on the core

SmolLM2-135M-Instruct's published weights through the runtime, greedy, at
F2's documented memory latency (as M5's and M6's real-data runs), each
token, logit and KV cache row checked bit for bit against the golden
model. The driver records the controller's handshakes with the units, so
each command's cycles are measured, from its start on its unit to its done,
and set against the perf model's (`verif/breakdown.py`).

## Tests

- `verif/tests/test_core.py` (driver `verif/bulk/core.cpp`): the tiny
  model through the runtime on the core at 4 and 32 ports, every token's

  the controller alone against stub units under random readiness and
  latencies, the tiny model's and SmolLM2's command lists; D-068's
  ordering rules on every handover, go and done; bad commands.
- `sw/tests/test_runtime.py`: the runtime on the golden platform
  (bit-exact, 4 and 32 ports), a new conversation, the end of the
  context, a device error, a device of another id.
- `model/tests/test_commands.py`: the command list's validation (a test
  per kind of bad command), the layout on D-040's channel offsets;
  `test_reporting.py`: this report.

  GB there, M6); each of its parts is. Vivado builds it in M9.

## Open issues

1. **The core's trace is not checked against D-068's ordering rules**
   (`verif/controller.py`'s `check` does it for the controller alone); the
   trace lacks the handover's unit and wait bits.
2. **The units never overlap** (above): the vector unit's share of a
   token adds to the engine's. Q-29, Q-30, Q-31 and Q-32 wait for F2's
   measurements (D-058).
3. **The controller's one-cycle handover** (decode, scoreboard and a
   unit's ready back to the command buffer's address) has no timing yet;
   if it fails 250 MHz, a registered decode costs 2 cycles a command
   (SmolLM2: about 5 µs more a token, estimate). M9's build.
4. **P's copy** (D-069): M9 adds up the design's on-chip memory before
   relying on it.
5. **For M9:** `OUTPUT` and the logits' way to the host (Q-33); the F2
   platform behind the runtime's six calls; the first Vivado build of the
   whole core.
